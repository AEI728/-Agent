# 保险 Agent 模拟面试与项目复盘问答

## 使用口径

- 目标岗位假设：AI 产品经理 / 互联网保险产品经理；采用完整项目面试口径。
- 已实现事实：个人/家庭动态分流、多轮结构化采集、规则式保障建议、候选方案对比工具、RAG 检索、LLM 适配层、来源展示、前端离线兜底、建议导出与隐私确认。
- 技术边界：当前 MVP 的 RAG 是本地 JSON 上的关键词重合检索，不是向量检索；正式 LLM 接口已预留，但默认运行在 Mock 模式；知识库共 150 条，已通过格式校验，但内容仍标记为待持证顾问/法务审核。
- 结果边界：文件夹中没有真实用户量、转化率、留存率、满意度、线上事故率或 A/B 实验数据。因此只能表述为“完成全链路功能验证”，不能表述为“验证了商业价值”或虚构增长数据。
- 口径冲突：题目中的“发现兴趣—加入学习—观看教程—AI 陪练—作品分享”及视频/语音陪练、社区互动属于银发教育/社区产品链路，不是当前保险 Agent 已实现功能。面试中应将其转换为保险旅程，不能硬说成项目成果。

| 原学习产品表达 | 保险 Agent 中的对应表达 |
| --- | --- |
| 发现兴趣 | 意识到保障风险或产生条款疑问 |
| 加入学习 | 发起个人/家庭咨询并同意隐私说明 |
| 观看教程 | 阅读险种、条款与避坑解释 |
| AI 陪练 | Agent 多轮追问、澄清与方案对比 |
| 作品分享 | 导出咨询摘要，与家庭成员或持证顾问复核 |

## 1. 你为什么选择做保险咨询 Agent？机会是怎么判断的？

**问题：** 保险咨询已经有经纪人、内容平台和产品对比工具，你为什么还要做一个 AI Agent？

**参考答案：**

我观察到消费者在保险决策中有三个连续障碍：第一是条款语言专业，用户看不懂；第二是产品责任和限制不在同一口径下，用户不会比较；第三是咨询常与销售转化绑定，用户担心被引导。它们不是一个搜索框就能解决的问题，因为用户往往连自己该问什么、缺什么信息都不知道。

因此我没有把 MVP 定义成“卖保险的机器人”，而是定义成“中立的需求梳理和保障教育工具”。它用多轮对话把模糊诉求转成画像，再基于知识检索给出险种、责任和条款的筛选原则，最后提供统一对比框架。AI 的价值不是替代核保或持证顾问，而是降低信息整理和理解成本，把一次非结构化咨询变成可复核的决策材料。

当前结果是产品和技术全链路已跑通，但这只证明方案可实现。市场需求强度、付费意愿和获客成本仍需通过访谈、可用性测试和真实流量验证。**需补充：实际访谈人数、原始证据、竞品样本和验证结论。**

**追问：**

1. 三个痛点里，哪个最值得优先解决？你用什么证据排序？
2. 如果用户最终仍要咨询销售，这个 Agent 的独立价值是什么？

## 2. 银发人群在这个项目中是什么位置？

**问题：** 你熟悉银发经济，那老年人是不是这个保险 Agent 的核心目标用户？他们的需求有什么不同？

**参考答案：**

我不会把“普通消费者”直接等同于“银发人群”。当前产品覆盖个人和家庭，银发用户更适合作为重点细分场景之一，包括老人本人咨询，以及子女替父母规划两类决策者。二者的数字能力、健康信息掌握程度、支付者和使用者关系都不同，不能共用一套话术。

在需求上，老年场景更关心基本医保是否连续、年龄和健康状况导致的可投范围、意外、防癌医疗和地方普惠保障；同时要避免用返还、收益等话术掩盖保障责任。现有规则中，年龄较高或健康异常会优先提示确认可投范围、关注意外和医疗兜底，这是一个初步分层，但还不是完整的银发产品研究。

若继续验证，我会分别招募“老人自主咨询”和“子女代办”用户，观察字体与操作、长文本理解、隐私顾虑、语音偏好、错误输入和家庭共同决策。**需补充：目前文件夹没有银发用户访谈、适老化可用性测试或无障碍验收结果，不能宣称已经验证。**

**追问：**

1. 子女给父母咨询时，谁是用户、谁是客户、谁提供健康信息？
2. 你会如何验证语音交互是否真的比文字更适合老人？

## 3. 你怎么看市场和竞品？为什么选择“对话式引导”而不是“AI 陪伴”？

**问题：** 这个项目为什么是 AI 陪伴产品？与保险经纪、测评内容和比价平台相比差异在哪里？

**参考答案：**

我会先纠正这个定义：保险是高风险、低频决策，核心价值是可信、可解释和可追溯，不应为了留存把它包装成强调情感依赖的“AI 陪伴”。我选择的是有温度的对话式引导，让用户愿意持续补充信息，但 Agent 必须保持中立边界，不能通过拟人化关系推动购买。

竞品可以按任务拆成四类：真人经纪擅长复杂个案但可能带销售立场；内容平台适合教育但无法结合用户情况；对比工具效率高但要求用户已经理解字段；通用大模型交互自然，但知识时效、引用和合规边界不稳定。我的取舍是把结构化采集、RAG、统一对比维度和合规兜底组合起来，重点解决“从不知道怎么问，到拿到可复核清单”的过程。

这仍是基于产品逻辑的判断。**需补充：竞品名单、任务实测记录、维度评分和差异化验证。** 面试中不要说“市场上没有类似产品”，而应说“我选择聚焦中立决策辅助，而不是销售成交”。

**追问：**

1. 如果保险公司自己也上线相同能力，你的壁垒是什么？
2. 中立定位如何商业化而不损害用户信任？

## 4. 目标用户如何分层？核心场景和优先级是什么？

**问题：** “普通消费者”太宽了，你具体服务谁？为什么先做个人/家庭分流？

**参考答案：**

我用“决策单元”和“保障责任”分层，而不仅按年龄分层。一级是个人规划和家庭规划：个人侧主要看年龄、职业、健康、已有保障和个人责任；家庭侧还要识别成员结构、主要收入来源、子女阶段、父母赡养、负债、家庭收支与长期目标。家庭不是多个个人的简单相加，还涉及谁应先保、预算如何分配、责任期限如何覆盖。

MVP 优先服务“有明确咨询意愿，但缺乏保险知识，尚未进入具体产品购买”的用户。因为这一阶段最需要需求澄清和教育，也能避开直接交易、个案核保和理赔裁定的高风险边界。对于明确购买、核保争议、理赔纠纷或大额传承，应转给保险公司、持证顾问或法律财务专业人士。

当前个人和家庭流程各有 11 个字段，证明了分流结构可以落地。**需补充：不同人群的规模、频次、痛点强度和完成率数据，才能证明优先级正确。**

**追问：**

1. 为什么“给父母投保”在当前逻辑里归入个体模式，而不是家庭模式？
2. 如果只能保留一个首发人群，你会选谁，依据是什么？

## 5. 你如何设计完整用户旅程和产品闭环？

**问题：** 请用一条端到端链路讲清楚用户从产生需求到完成决策的过程。

**参考答案：**

保险场景的闭环不是“发现兴趣—学习—陪练—晒作品”，而是“风险触发—发起咨询—完成画像—理解方案—统一对比—线下核验/转人工”。用户可能因结婚、生育、父母变老、已有保单盘点或销售推荐产生疑问；进入产品后先确认隐私说明，再选择个人或家庭模式；Agent 分步采集关键信息；画像完成后输出保障顺序、优质产品画像、避坑项、条款阅读指南和候选产品验算表；最后用户可导出摘要，与家人或专业人士复核。

这个闭环里，AI 不承担最终成交。它承担的是把用户从“模糊焦虑”推进到“可比较、可提问、可复核”。当前已实现咨询、建议、对比和导出，后端不可用时保留前端规则建议；尚未实现真实产品数据接入、持证顾问工单、家庭协作状态或购买后的保单管理。

**假设：** 若后续做持续服务，合理方向是保单年检、政策更新提醒和家庭保障缺口变化，而不是为了活跃度引入与保险决策无关的作品社区。

**追问：**

1. 这条链路最可能在哪一步流失？你如何验证？
2. 导出摘要之后，怎样知道用户是否真的完成了下一步决策？

## 6. 状态机工作流是怎么设计的？为什么不用完全自由对话？

**问题：** 你提到用状态机驱动多轮咨询，具体状态、跳转和结束条件是什么？

**参考答案：**

任务是把咨询需要的信息采齐，因此我把流程设计成“当前字段—答案标准化—画像更新—寻找下一缺失字段—完成后生成建议”。入口字段先识别个人或家庭，并切换两套字段序列。个人侧包括意图、年龄、性别、需求、城市、职业、家庭责任、负债、已有保障、预算和健康；家庭侧替换为家庭成员、子女、父母赡养、家庭收支和长期目标等字段。所有必需字段都有值后进入完成态。

选择状态机，是为了保证高风险场景的信息完整性、流程可解释性和可测试性。完全自由对话虽然自然，但容易漏问健康、预算或已有保障，也难定位错误。为了减少机械感，我允许用户在非开放字段中一次表达多个信息，由规则尝试补全其他字段；同时在开放字段中保留原话，避免过度压缩。

当前状态保存在前端内存中，尚无会话持久化、回退到指定字段的完整编辑器或并发会话管理。面试中应将其称为 MVP 状态机，不应描述为成熟编排平台。

**追问：**

1. 用户中途修改“个人”为“家庭”，已有字段如何迁移或失效？
2. 哪些字段是强制项，哪些可以跳过？依据是什么？

## 7. 为什么采用“固定选项 + 开放式输入”？如何处理准确性和效率的冲突？

**问题：** 固定选项可能限制表达，开放输入又难结构化，你是怎么取舍的？

**参考答案：**

我的决策原则是按字段的信息熵和风险分型。年龄区间、性别、城市层级、职业类型、预算区间、保障诉求等适合固定选项，降低认知成本并便于后续规则判断；家庭结构、负债、已有保障和健康情况需要上下文，采用开放输入，并在问题里给出不含真实姓名的示例，告诉用户需要什么粒度。

输入后做两层处理：当前字段先归一化，例如把金额映射到预算区间、把自然语言意图映射为个人或家庭；若用户一句话中包含年龄、职业、健康等多个信号，再尝试补齐尚未填写的字段。开放字段保留较长文本，其他字段控制长度，以兼顾画像质量和界面可读性。

这个方案的风险是关键词规则可能误判、压缩掉关键信息。例如“没有异常”中包含“异常”，复杂否定和多人的健康信息也容易被错误归类。后续应加入确认卡，让用户在进入推荐前逐项复核，并把“低置信度/多义输入”转为澄清问题。**需补充：各字段识别准确率和用户修改率。**

**追问：**

1. 如何定义一条采集结果“足够完整”？
2. 如果用户拒绝回答健康或收入，产品还应不应该给建议？

## 8. Agent 的人设、语气和 Prompt 是怎么设计的？

**问题：** “小安”这个人设如何影响回答？你如何防止它变成有销售感的客服？

**参考答案：**

“小安”的人设目标不是高度拟人，而是降低第一次谈论健康、负债和预算时的压力。语气应温和、克制、解释原因，提问时说明“为什么需要这项信息”，并避免催促、恐吓和绝对化表述。用户需要感到被理解，但不能产生“它替我做最终决定”的错觉。

系统 Prompt 明确了四层边界：第一，只做中立需求梳理和保障教育；第二，不承诺承保、理赔或具体产品结果，也不点名推荐产品；第三，每个相关险种都补充可核验指标、避坑点、条款阅读和对比方法；第四，区分事实、建议和不确定性，外部知识只能引用检索上下文真实存在的来源。

我把语气和任务约束放在同一 Prompt 中，但生产化还需要把硬性禁用规则做成模型外校验，不能只依赖提示词。**需补充：Prompt 版本、对照测试和人工评分结果。**

**追问：**

1. 哪些约束应该写在 Prompt，哪些必须由代码保证？
2. 如果“温和”导致回答冗长、用户退出，你会怎么调？

## 9. 意图识别、异常输入和降级兜底怎么做？

**问题：** 用户不按你的问题回答、一次说很多信息，或者后端挂了，系统怎么办？

**参考答案：**

当前 MVP 采用可解释的规则识别：对个人/家庭、年龄、职业、需求、预算、健康等字段设置关键词和格式规则；一次输入命中多个尚未填写字段时可以并行补全；无法标准化时保留截断后的原始文本，而不是直接丢弃。这样适合早期快速定位 Bad Case，但不适合覆盖复杂否定、多人信息和跨轮指代。

异常处理分三层：输入层对空值和重复提交做拦截；对话层应在低置信度时澄清并允许修改画像，当前仅实现了有限的重新确认，需继续完善；服务层在 `/api/chat` 不可用时，前端仍展示规则式保障建议，避免主流程完全失败。后端接口异常则返回统一错误，不向用户暴露密钥或内部堆栈。

下一步我会为每个字段定义置信度、必填性和兜底动作，并重点覆盖否定句、信息冲突、给他人咨询、多成员健康差异、超长输入、诱导具体产品和越权理赔判断等 Bad Case。

**追问：**

1. 规则识别和大模型识别冲突时，以谁为准？
2. 你会如何设计“转人工”的触发条件和上下文交接？

## 10. RAG 知识库是怎么做的？如何保证回答可解释？

**问题：** 你简历里写了 RAG，具体检索、知识结构和引用机制是什么？

**参考答案：**

MVP 知识库用 6 个结构化 JSON 文件管理 150 条内容，覆盖保险概念、社保医保、四大险种、配置规则、FAQ 和合规规则。每条要求有 ID、类型、标题、来源、审核人和更新时间；服务启动后加载到内存。检索会对用户问题和画像做中英文规范化与中文二元切分，按 token 重合度打分，默认返回 Top 4，再把命中的正文放进 LLM 上下文，前端展示标题来源。

选择关键词检索而不是一开始上向量数据库，是 MVP 的资源取舍：知识量小、查询路径透明、调试成本低，足以验证“检索—生成—引用”的接口边界。未来可以在 `KnowledgeStore` 层替换为 Embedding 和向量库，而不改上层对话协议。

但我不会把当前版本说成生产级 RAG。它没有语义召回、重排、引用句级绑定、时效自动失效或权威性评分；知识条目的 `source` 多为内部方法论标签，且审核状态仍为待审核。上线前必须接入官方来源、版本日期和专业审核，并建立检索召回与忠实度评测。

**追问：**

1. 如何证明 RAG 比直接让模型回答更好？
2. 政策和条款发生变化时，如何避免旧知识继续被检索？

## 11. 保险场景的安全、隐私和合规如何设计？

**问题：** AI 给保险建议风险很高，你如何防止误导、隐私泄露和越权推荐？

**参考答案：**

我把风险按输入、生成、输出和转人工四段控制。输入侧只收完成需求画像所需信息，示例明确无需姓名，启动前展示隐私说明；API Key 只在后端环境变量中。生成侧通过系统 Prompt 限制为教育和需求梳理，不点名产品，不承诺承保、理赔和收益。输出侧反复提醒以最新官方条款、费率和核保结论为准，并要求比较保险责任、免责、释义、健康告知等维度。转人工侧对个案核保、理赔争议、合同法律解释、大额传承和明确购买决策交给相应专业人员。

知识库还设置了禁止保证收益、禁止绝对价格结论、禁止承诺赔付、必须提醒如实告知和地区时效等规则。当前不足是这些规则主要依赖 Prompt 和内容规范，没有独立的输入脱敏、敏感信息检测、输出审核、审计日志、权限和留存策略；而且知识尚未完成持证顾问/法务审核。

因此 MVP 可以用于演示和封闭验证，但不能直接作为正式投保建议系统上线。生产化的门槛应是“权威知识 + 专业审核 + 模型外硬规则 + 可追溯日志 + 明确转人工”。

**追问：**

1. 用户主动输入身份证号或完整病历时，你怎么处理？
2. 如果模型引用了真实来源，却基于来源做出错误推论，责任如何控制？

## 12. 个性化推荐、对比工具和持续使用如何形成价值？

**问题：** 你如何实现个性化？题目里提到视频/语音、作品分享和社区互动，这些怎么落到保险项目？

**参考答案：**

当前个性化是规则和画像驱动，而不是黑盒推荐。系统根据个人/家庭、年龄、健康复杂度、职业风险和家庭责任切换建议：例如家庭模式先分成员和家庭支柱；年龄较高时更关注医保、意外、防癌医疗或普惠保障；健康异常时先确认可投范围；有负债和抚养责任时提高定期寿险的重要性。最终不输出具体商品，而是给出险种顺序、建议区间、检查清单和统一对比维度。

对比工具让用户手动录入候选产品的保额、年保费、等待期和关键限制，系统只做单位保额保费和等待期等提示，并明确“低价不代表保障更好”。这符合中立定位，也让建议可被用户拿着官方条款复核。

视频/语音可以作为未来的适老化解释方式，例如语音问答、条款逐段朗读和短视频知识卡，但必须先验证使用需求及误听风险；“作品分享”不适合保险，应改成可控的咨询摘要导出和家庭共同确认；开放社区可能放大错误建议、营销和隐私泄露，MVP 不应优先。持续价值更适合来自保单年检、家庭变化和政策更新提醒。以上均为**假设/后续方案，不是已上线功能**。

**追问：**

1. 规则个性化到什么程度会变成变相产品推荐？
2. 为什么不做社区？在什么条件下你会重新考虑？

## 13. 你会怎么定义北极星指标和漏斗？

**问题：** 这个产品的北极星指标是什么？你会看哪些过程和质量指标？

**参考答案：**

MVP 阶段我不会把 DAU、对话轮数或最终投保量作为北极星。DAU 不适合低频保险决策，对话轮数越长也未必越好，投保量则可能把 Agent 推向销售导向。我更倾向定义为“有效保障决策完成数/率”：用户完成关键画像，查看了方案和条款对比，并执行了导出、候选对比或转专业人员复核中的至少一个有效动作。它同时约束完成度和决策价值。

漏斗可拆为：进入咨询 → 同意隐私说明 → 选择个人/家庭 → 完成首个核心字段 → 完成画像 → 查看建议 → 使用对比工具 → 导出/转人工。过程指标包括各字段退出率、平均澄清次数、画像修改率、建议生成成功率和 RAG 命中率。质量指标包括字段识别准确率、引用忠实度、合规通过率、建议可理解度、用户信任度和专业审核一致性。持续指标可看 7/30 天回访，但应按保单盘点或家庭事件等有意义行为解释，而不是机械追求留存。

当前项目未接入埋点，也没有真实漏斗、留存、完课或社区互动数据。**需补充：若你做过人工原型测试，应填入样本量、任务完成率、关键观察和迭代前后变化；没有数据就只讲指标设计。**

**追问：**

1. “有效决策完成”如何防止被产品自己刷高？
2. 用户满意但建议错误，与用户不满意但建议合规，你怎么权衡？

## 14. Bad Case 评测集和 0-1 验证闭环是怎么做的？

**问题：** 你说建立了评测与迭代闭环，具体评什么、怎么迭代、验证到了什么程度？

**参考答案：**

按简历描述，我把典型用户提问和测试中暴露的问题沉淀为 Bad Case，评测对象不是只看最终文案，而是覆盖整条链路：意图分流是否正确、字段是否采全、归一化是否失真、是否检索到相关知识、建议是否符合画像、对比维度是否完整、引用是否真实、是否触发合规或转人工。

分类上至少包括模糊诉求、一次输入多字段、否定句、个人/家庭冲突、代父母或孩子咨询、老人慢病、高危职业、预算不足、已有保障不清、诱导点名产品、承诺理赔、无来源政策问题和后端不可用。每个 Case 应记录输入、期望状态/输出、实际结果、错误类型、严重级别、归因、修复版本和回归结果。修复可能落在分流正则、采集字段、推荐规则、Prompt、知识条目或降级策略，而不是一律调 Prompt。

目前仓库能验证的是代码语法、6 个知识文件的数量、必填字段和重复 ID；`npm run check` 已通过，共 150 条。仓库中没有 Bad Case 数据文件、评分标准、版本对比或真实用户反馈记录。因此严谨表述是“已建立评测思路并完成全链路功能验证”；若确有线下评测，**需补充：Case 数量、通过率、Top 问题、至少一个迭代前后实例及参与者。**

**追问：**

1. 请现场讲一个最有价值的 Bad Case，以及它如何改变产品设计。
2. 你如何区分模型问题、检索问题、规则问题和产品流程问题？

## 15. 0-1 落地时如何协作、取舍资源？最大的风险和复盘是什么？

**问题：** 如果这是你主导的 0-1 项目，你如何推动设计、研发、保险专家和法务协作？做了哪些取舍？

**参考答案：**

在目标上，我先把团队对齐到“中立需求梳理 MVP”，而不是“自动卖保险”。这直接决定三个资源取舍：第一，不接真实商品库和交易，先验证画像、建议和对比链路；第二，不一开始建设向量数据库，先用 150 条结构化知识和关键词检索跑通 RAG 接口；第三，保留前端规则式建议作为稳定基线，正式 LLM 通过后端适配层接入，避免模型或接口失败导致主流程不可用。

协作上，产品负责用户旅程、字段字典、状态跳转、推荐边界和验收 Case；研发负责前后端状态、检索和 LLM 接口；设计重点验证长流程负担、敏感信息表达和适老可用性；持证顾问审核配置逻辑与术语；法务/合规审核知识来源、禁用表述、隐私授权和转人工边界。推进时用一张“场景—字段—规则—知识—风险—验收 Case”矩阵，避免各团队只看自己的交付物。

复盘看，做对的是先把高不确定性的咨询过程结构化，并提前设置不点名产品、引用来源和降级兜底。最大不足是验证层还偏工程可运行：知识源权威性不足且未完成专业审核，评测资产未在仓库沉淀，没有用户行为数据，也没有真实转人工闭环。下一阶段不应先堆功能，而应先补用户研究、专业审核、评测基线和埋点，再决定是否扩展语音、保单管理或顾问协同。

**追问：**

1. 如果只有两周和一名研发，你会保留什么、砍掉什么？
2. 项目里哪个决策如果重来一次你会改变？为什么？

以下信息不在当前文件夹中。建议面试前按真实情况补齐，不要估算或包装：

6. 数据结果：只有确有埋点或记录时，才写完成率、准确率、满意度、留存或转化变化。

## 30 秒项目总结

我做的是一个中立保险规划 Agent，核心不是替用户买保险，而是解决“看不懂、不会比、怕被误导”。我用个人/家庭双状态机把模糊诉求采集成结构化画像，再通过规则建议、RAG 知识检索和统一条款对比框架，帮助用户形成可复核的保障方案；同时通过不点名产品、来源引用、免责声明和转人工边界控制风险。当前完成的是 0-1 MVP 全链路和知识库校验，下一步重点不是继续堆功能，而是补齐专业审核、Bad Case 基线、用户验证和埋点闭环。
